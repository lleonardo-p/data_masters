# ADR-017: Estratégia de Deploy e Infraestrutura como Código

- **Status:** Aceito
- **Data:** 2026-07-05
- **Decisores:** Leonardo Lucas Pereira

---

## Contexto

O BAIP utiliza múltiplos serviços AWS, incluindo:

- Amazon S3;
- AWS Glue;
- AWS Glue Data Catalog;
- Amazon Athena;
- Amazon SQS;
- AWS Lambda;
- Amazon DynamoDB;
- AWS Step Functions;
- Amazon EventBridge;
- Amazon CloudWatch;
- AWS IAM;
- AWS KMS;
- AWS Secrets Manager.

Criar e manter esses recursos manualmente aumenta o risco de inconsistência, dificulta reprodução do ambiente e reduz governança.

É necessário definir uma estratégia de deploy e provisionamento da infraestrutura.

Foram consideradas as seguintes alternativas:

- Terraform;
- AWS CloudFormation;
- AWS CDK;
- AWS SAM;
- criação manual via console.

---

## Decisão

Será utilizado **Terraform** como ferramenta principal de Infraestrutura como Código (IaC) do BAIP.

A infraestrutura será versionada no repositório do projeto e organizada em módulos reutilizáveis.

---

## Princípios

A estratégia de IaC seguirá os seguintes princípios:

- nenhum recurso crítico deve ser criado manualmente;
- toda infraestrutura deve ser versionada;
- mudanças devem passar por revisão;
- ambientes devem ser reproduzíveis;
- permissões devem seguir o princípio do menor privilégio;
- secrets não devem ser commitados;
- configurações sensíveis devem ser parametrizadas;
- recursos devem possuir tags padronizadas.

## Justificativa

Terraform foi escolhido por ser amplamente utilizado no mercado, possuir suporte maduro à AWS e permitir organização modular da infraestrutura.

Essa escolha também reforça o caráter profissional do projeto, demonstrando práticas modernas de Engenharia de Dados, Cloud Engineering e DevOps.

CloudFormation e CDK são boas alternativas nativas da AWS, mas Terraform oferece maior familiaridade de mercado e portabilidade conceitual.

---

## Alternativas Consideradas

### Terraform

**Resultado:** Selecionado.

**Vantagens**

- amplamente utilizado no mercado;
- suporte maduro à AWS;
- organização modular;
- boa legibilidade;
- independência relativa do provedor;
- adequado para portfólio;
- facilita reprodução de ambientes.

**Desvantagens**

- exige gerenciamento de state;
- exige cuidado com secrets;
- pode gerar drift se recursos forem alterados manualmente;
- curva de aprendizado inicial.

---

### AWS CloudFormation

**Resultado:** Não selecionado.

**Vantagens**

- nativo AWS;
- integrado ao ecossistema AWS;
- sem necessidade de ferramenta externa.

**Desvantagens**

- menos flexível que Terraform;
- templates podem ficar verbosos;
- menor portabilidade conceitual.

---

### AWS CDK

**Resultado:** Não selecionado para o MVP.

**Vantagens**

- permite definir infraestrutura com linguagens de programação;
- boa integração com AWS;
- mais expressivo que CloudFormation puro.

**Desvantagens**

- maior abstração;
- exige conhecimento adicional;
- menos direto para leitura por recrutadores que esperam IaC declarativo.

---

### AWS SAM

**Resultado:** Não selecionado como solução principal.

**Vantagens**

- bom para aplicações serverless;
- simplifica deploy de Lambda e API Gateway.

**Desvantagens**

- escopo mais limitado;
- não cobre tão bem toda a infraestrutura de dados;
- menos adequado como IaC principal da plataforma.

---

### Criação Manual via Console

**Resultado:** Rejeitada.

**Vantagens**

- rápida para testes pontuais.

**Desvantagens**

- não reproduzível;
- alto risco de erro;
- difícil auditoria;
- gera drift;
- inadequado para uma arquitetura profissional.

---

## Consequências

### Positivas

- infraestrutura versionada;
- ambientes reproduzíveis;
- maior governança;
- menor risco de configuração manual;
- facilidade de revisão;
- melhor apresentação do projeto como case profissional.

### Negativas

- necessidade de gerenciar state;
- aumento da complexidade inicial;
- necessidade de padronizar módulos;
- risco de drift se houver alterações manuais.

---

## Riscos

- state remoto mal configurado;
- secrets expostos no código;
- permissões IAM amplas demais;
- drift entre Terraform e AWS;
- destruição acidental de recursos;
- falta de revisão em mudanças críticas.

---

## Mitigações

- uso de backend remoto para state;
- bloqueio de alterações manuais em recursos críticos;
- uso de variáveis e secrets seguros;
- revisão de Pull Requests;
- princípio do menor privilégio;
- uso de `terraform plan` antes de aplicar mudanças;
- separação por ambiente;
- tags obrigatórias;
- documentação dos módulos.

---

## Estratégia de Deploy

O fluxo de deploy será:

```text
Desenvolvedor
    │
    ▼
Pull Request
    │
    ▼
Review
    │
    ▼
Terraform Plan
    │
    ▼
Terraform Apply
    │
    ▼
AWS Resources
```

No MVP, o `terraform apply` poderá ser executado manualmente. Em uma evolução futura, o deploy poderá ser automatizado via GitHub Actions.

---

## Decisão Final

O BAIP utilizará **Terraform** como ferramenta principal de Infraestrutura como Código.

Essa decisão garante uma infraestrutura versionada, reproduzível, auditável e alinhada com práticas modernas de arquitetura cloud e engenharia de dados.
