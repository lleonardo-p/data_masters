# ADR-008: Escolha do Store para Indicadores Near Real-Time

- **Status:** Aceito
- **Data:** 2026-07-05
- **Decisores:** Leonardo Lucas Pereira

---

## Contexto

O BAIP precisa armazenar indicadores epidemiológicos atualizados em tempo quase real a partir dos eventos de triagem hospitalar.

Esses indicadores serão utilizados para monitoramento operacional e posterior sincronização com a camada Gold e o Data Warehouse.

Exemplos de indicadores near real-time:

```text
SP#2026-07-03#DENGUE       → total_cases = 501
SP#2026-07-03#ZIKA         → total_cases = 37
RJ#2026-07-03#CHIKUNGUNYA  → total_cases = 89
```

O store near real-time deve atender aos seguintes requisitos:

- baixa latência de escrita;
- atualização atômica de contadores;
- acesso por chave;
- escalabilidade;
- alta disponibilidade;
- baixa complexidade operacional;
- integração simples com AWS Lambda;
- armazenamento apenas de dados agregados;
- ausência de PII;
- sincronização posterior com Gold e Data Warehouse.

Foram consideradas as seguintes alternativas:

- Amazon DynamoDB;
- Redis / Amazon ElastiCache;
- Amazon Aurora.

---

## Decisão

Será utilizado **Amazon DynamoDB** como store near real-time para indicadores agregados do BAIP.

O DynamoDB armazenará contadores e métricas agregadas por chave analítica, como data, UF, município e doença.

---

## Arquitetura Proposta

```text
AWS Lambda
    │
    ▼
Amazon DynamoDB
    │
    ▼
Realtime Gold Sync Job
    │
    ▼
Gold Data Lake
    │
    ▼
Data Warehouse
    │
    ▼
Dashboard
```

---

## Papel do DynamoDB na Arquitetura

O DynamoDB será utilizado como store operacional para indicadores near real-time.

Ele não substituirá a camada Gold nem o Data Warehouse.

Seu papel será:

- armazenar contadores atualizados rapidamente;
- permitir atualização atômica de métricas;
- servir como camada operacional temporária de indicadores;
- disponibilizar dados para sincronização com a camada Gold;
- apoiar dashboards ou APIs operacionais quando necessário.

---

## Modelo de Chave

A modelagem será orientada aos principais padrões de acesso.

Exemplo de chave única:

```text
PK = UF#DATA#DOENCA
```

Exemplo:

```text
PK = SP#2026-07-03#DENGUE
total_cases = 501
last_update = 2026-07-03T10:30:00
source = hospital_si
```

Outra possibilidade é utilizar partition key e sort key:

```text
PK = UF#DOENCA
SK = DATA
```

Exemplo:

```text
PK = SP#DENGUE
SK = 2026-07-03
total_cases = 501
last_update = 2026-07-03T10:30:00
```

---

## Exemplo de Atualização

Quando um novo evento de triagem é processado, a Lambda atualiza o contador correspondente.

Exemplo lógico:

```text
PK = SP#2026-07-03#DENGUE
ADD total_cases + 1
SET last_update = current_timestamp
```

Essa abordagem permite atualização incremental de indicadores sem necessidade de recalcular toda a base analítica.

---

## Justificativa

O DynamoDB foi escolhido porque o caso de uso do BAIP é baseado em atualização rápida de indicadores agregados por chave.

A solução é adequada porque:

- permite atualização atômica de contadores;
- possui baixa latência;
- integra-se facilmente com AWS Lambda;
- é totalmente gerenciada;
- não exige administração de servidores;
- é adequada para acesso key-value;
- suporta escalabilidade conforme o volume de eventos aumenta;
- evita a necessidade de manter um banco relacional apenas para contadores simples.

Para o BAIP, os dados near real-time não exigem joins complexos nem consultas relacionais. O principal requisito é atualizar contadores rapidamente e disponibilizar esses indicadores para sincronização posterior com a camada Gold.

## Alternativas Consideradas

### Amazon DynamoDB

**Resultado:** Selecionado.

**Vantagens**

- baixa latência;
- atualização atômica de contadores;
- arquitetura serverless;
- alta escalabilidade;
- integração nativa com Lambda;
- adequado para chave-valor;
- baixo esforço operacional;
- boa opção para indicadores agregados near real-time.

**Desvantagens**

- não é ideal para consultas analíticas complexas;
- exige bom desenho de chave;
- não é adequado para joins;
- modelagem orientada ao padrão de acesso;
- não substitui o Data Warehouse.

---

### Redis / Amazon ElastiCache

**Resultado:** Não selecionado como store principal.

**Vantagens**

- latência extremamente baixa;
- bom para cache;
- adequado para rankings, sessões e dados temporários;
- alta performance em memória;
- pode ser útil para acelerar dashboards.

**Desvantagens**

- mais adequado como cache do que como store principal de indicadores;
- exige maior cuidado com persistência e durabilidade;
- adiciona complexidade operacional;
- menos alinhado ao objetivo de consolidar indicadores para Gold/DW;
- não é necessário para o SLA inicial do BAIP.

---

### Amazon Aurora

**Resultado:** Não selecionado para o store near real-time.

**Vantagens**

- banco relacional robusto;
- suporte a SQL;
- bom para transações;
- adequado para joins e consultas operacionais complexas;
- útil para sistemas transacionais tradicionais.

**Desvantagens**

- maior complexidade para o caso de contadores simples;
- custo e operação superiores ao necessário para o MVP;
- menos aderente a atualizações atômicas simples por chave;
- não é necessário para o padrão de acesso do BAIP;
- exigiria modelagem relacional mais complexa sem ganho proporcional.

---

## Consequências

### Positivas

- baixa latência para atualização de indicadores;
- menor esforço operacional;
- integração direta com Lambda;
- suporte a contadores atômicos;
- arquitetura serverless;
- dados near real-time isolados do Data Warehouse;
- facilidade de sincronização posterior com a camada Gold;
- ausência de PII no store operacional.

### Negativas

- necessidade de desenhar bem as chaves;
- consultas exploratórias são limitadas;
- não substitui o Data Warehouse;
- exige sincronização com Gold para consumo analítico consolidado;
- risco de hot partition se a chave for mal definida.

---

## Riscos

- hot partition em chaves muito concentradas;
- duplicidade de eventos causando supercontagem;
- dificuldade de consulta caso o modelo de chave seja mal definido;
- divergência temporária entre DynamoDB e Gold;
- uso indevido do DynamoDB como camada analítica principal;
- crescimento descontrolado de registros sem política de retenção.

---

## Mitigações

- uso de `event_id` para idempotência;
- desenho de chave baseado nos principais padrões de acesso;
- monitoramento de consumo e throttling;
- sincronização periódica com Gold;
- validação de consistência entre indicadores batch e near real-time;
- armazenamento apenas de dados agregados e sem PII;
- uso do Data Warehouse como fonte oficial para análises históricas consolidadas;
- definição de política de retenção para indicadores operacionais;
- alarmes para erro de escrita, throttling e divergência de contadores.

---

## Estratégia de Sincronização com Gold

O DynamoDB será utilizado como store operacional near real-time.

A camada Gold e o Data Warehouse continuarão sendo as fontes principais para consumo analítico consolidado.

Fluxo proposto:

```text
DynamoDB
    │
    ▼
Realtime Gold Sync Job
    │
    ▼
Gold Data Lake
    │
    ▼
Data Warehouse
    │
    ▼
Dashboard
```

A sincronização poderá ocorrer em intervalos curtos, como a cada 1 minuto, consolidando os indicadores near real-time na camada analítica.

---

## Relação com o Data Warehouse

O DynamoDB não será utilizado como Data Warehouse.

O papel de cada camada será:

```text
DynamoDB
→ indicadores operacionais near real-time

Gold Data Lake
→ datasets analíticos consolidados

Data Warehouse
→ fatos, dimensões, KPIs e consumo por dashboards
```

O Dashboard poderá consultar a camada analítica consolidada, evitando acoplamento direto com o store operacional.

---

## Decisão Final

Para o BAIP, **Amazon DynamoDB** é a melhor opção para armazenar indicadores near real-time por oferecer baixa latência, atualizações atômicas, integração nativa com Lambda e baixa complexidade operacional.

Redis/ElastiCache poderá ser considerado futuramente como camada de cache para dashboards de alta frequência, enquanto Aurora poderá ser utilizado em um sistema operacional separado caso surjam necessidades relacionais mais complexas.
