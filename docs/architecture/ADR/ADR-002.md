# ADR-002: Escolha da Solução de Armazenamento do Data Lake

- **Status:** Aceito
- **Data:** 2026-07-04
- **Decisores:** Leonardo Lucas Pereira

---

## Contexto

O BAIP precisa armazenar dados provenientes de múltiplas fontes, incluindo APIs públicas de saúde, clima, eventos ambientais e sistemas hospitalares simulados.

A solução deve permitir armazenamento escalável, baixo custo, separação entre dados brutos e tratados, reprocessamento, auditoria, consulta analítica e evolução para um modelo Lakehouse.

Foram consideradas as seguintes alternativas:

- Amazon S3
- Amazon Redshift
- Amazon RDS / PostgreSQL
- Amazon DynamoDB
- Armazenamento local ou on-premises

---

## Decisão

O projeto utilizará **Amazon S3** como camada principal de armazenamento do Data Lake.

Os dados serão organizados seguindo a arquitetura **Medallion**, com as camadas:

- **Bronze**: dados brutos extraídos das fontes;
- **Silver**: dados tratados, padronizados e enriquecidos;
- **Gold**: dados analíticos, agregações, fatos, dimensões e indicadores.

---

## Justificativa

O Amazon S3 foi escolhido por ser um serviço gerenciado, escalável, durável e adequado para armazenamento de grandes volumes de dados.

Além disso, o S3 possui integração nativa com serviços de Engenharia de Dados e Analytics da AWS, como AWS Glue, AWS Glue Data Catalog e Amazon Athena.

Essa escolha permite:

- armazenar dados em diferentes formatos;
- separar dados brutos, tratados e analíticos;
- realizar reprocessamentos;
- reduzir custo inicial;
- escalar o volume de dados conforme o projeto evolui;
- consultar dados diretamente no Data Lake por meio de engines analíticas.

---

## Consequências

### Positivas

- baixo custo de armazenamento;
- alta escalabilidade;
- separação clara entre Bronze, Silver e Gold;
- suporte a reprocessamento e auditoria;
- integração com Glue, Athena e Data Catalog;
- base adequada para arquitetura Lakehouse.

### Negativas

- exige cuidado com organização de arquivos e particionamento;
- pode gerar muitos arquivos pequenos se mal projetado;
- não substitui, sozinho, um banco analítico otimizado;
- depende de catálogo externo para consultas estruturadas.

---

## Alternativas Consideradas

### Amazon Redshift

**Resultado:** Não selecionado como armazenamento principal.

**Vantagens**

- banco analítico robusto;
- bom desempenho para consultas SQL;
- adequado para Data Warehouse tradicional.

**Desvantagens**

- maior custo;
- menor flexibilidade para armazenar dados brutos;
- menos adequado como primeira camada de Data Lake.

---

### Amazon RDS / PostgreSQL

**Resultado:** Não selecionado.

**Vantagens**

- simples para dados estruturados;
- bom para aplicações transacionais.

**Desvantagens**

- não é ideal para grande volume analítico;
- menor flexibilidade para dados semi-estruturados;
- custo e escalabilidade menos adequados para Data Lake.

---

### Amazon DynamoDB

**Resultado:** Não selecionado como Data Lake.

**Vantagens**

- baixa latência;
- boa escolha para indicadores near real-time.

**Desvantagens**

- não é adequado para armazenamento histórico analítico;
- não é ideal para modelagem dimensional ou consultas exploratórias.

---

### Armazenamento Local / On-Premises

**Resultado:** Não selecionado.

**Vantagens**

- maior controle da infraestrutura.

**Desvantagens**

- maior esforço operacional;
- menor elasticidade;
- maior complexidade de manutenção;
- menos adequado ao objetivo do projeto.

---

## Riscos

- crescimento desorganizado do Data Lake sem padronização de pastas;
- custos elevados caso não exista política de retenção;
- baixa performance em consultas se não houver particionamento adequado;
- acúmulo de arquivos pequenos.
