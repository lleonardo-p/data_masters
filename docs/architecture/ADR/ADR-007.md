# ADR-007: Escolha do Processador Near Real-Time

- **Status:** Aceito
- **Data:** 2026-07-05
- **Decisores:** Leonardo Lucas Pereira

---

## Contexto

Após o recebimento dos eventos de triagem hospitalar na camada de mensageria, o BAIP precisa processar esses eventos em tempo quase real.

O processamento near real-time será responsável por consumir mensagens da fila, validar o conteúdo recebido, resolver a identidade do paciente, remover ou pseudonimizar dados PII, persistir o evento tratado e atualizar indicadores agregados.

O processamento deve atender aos seguintes requisitos:

- integração simples com a solução de mensageria;
- execução orientada a eventos;
- baixa latência;
- escalabilidade automática;
- baixo custo para cargas variáveis;
- baixa complexidade operacional;
- suporte a retentativas;
- tratamento de falhas;
- execução sem necessidade de gerenciamento de servidores;
- processamento de eventos em até 1 minuto após a chegada da mensagem.

Foram consideradas as seguintes alternativas:

- AWS Lambda;
- Amazon ECS / AWS Fargate;
- AWS Glue Streaming.

---

## Decisão

Será utilizado **AWS Lambda** como processador near real-time dos eventos de triagem hospitalar.

A função Lambda será acionada a partir de mensagens disponíveis na fila SQS e será responsável por processar os eventos de forma assíncrona.

---

## Arquitetura Proposta

```text
Amazon SQS Queue
        │
        ▼
AWS Lambda
        │
        ├── Identity Service
        │
        ├── Silver Data Lake
        │
        └── Realtime Indicator Store
```

---

## Responsabilidades da Lambda

A função Lambda será responsável por:

1. Consumir mensagens da fila SQS;
2. Validar o schema do evento;
3. Verificar duplicidade por meio do `event_id`;
4. Resolver a identidade do paciente via Identity Service;
5. Remover dados PII antes da persistência analítica;
6. Persistir o evento tratado na camada Silver;
7. Atualizar indicadores agregados no store near real-time;
8. Registrar métricas de processamento;
9. Encaminhar mensagens inválidas para tratamento por DLQ.

## Justificativa

AWS Lambda foi escolhida porque o processamento esperado para cada evento é curto, assíncrono e orientado a eventos.

A solução é adequada para o BAIP porque:

- integra-se diretamente com Amazon SQS;
- escala automaticamente conforme o volume de mensagens;
- elimina a necessidade de gerenciar servidores;
- possui baixo custo para cargas intermitentes;
- simplifica o desenvolvimento do MVP;
- mantém a arquitetura serverless;
- atende ao requisito de processamento near real-time.

O processamento de eventos de triagem não exige um serviço long-running nem processamento distribuído Spark em tempo real. Por isso, Lambda é mais adequada do que ECS/Fargate ou Glue Streaming para o escopo atual.

## Alternativas Consideradas

### AWS Lambda

**Resultado:** Selecionada.

**Vantagens**

- arquitetura serverless;
- integração nativa com SQS;
- escalabilidade automática;
- baixo custo para eventos esporádicos;
- baixa complexidade operacional;
- boa aderência a processamento curto e orientado a evento;
- suporte a retry;
- integração com CloudWatch para logs e métricas.

**Desvantagens**

- limite de tempo de execução;
- menos adequada para workloads long-running;
- exige cuidado com idempotência;
- cold start pode impactar latência em alguns cenários;
- exige atenção à configuração de batch size, timeout e visibility timeout.

---

### Amazon ECS / AWS Fargate

**Resultado:** Não selecionado para o escopo atual.

**Vantagens**

- maior controle sobre runtime;
- adequado para containers;
- bom para serviços long-running;
- permite dependências mais complexas;
- flexível para aplicações customizadas.

**Desvantagens**

- maior complexidade de configuração;
- maior esforço operacional;
- custo potencialmente maior para cargas pequenas;
- exige definição de tasks, services, networking e escalabilidade;
- excesso de capacidade para processamento simples de eventos.

---

### AWS Glue Streaming

**Resultado:** Não selecionado para o escopo atual.

**Vantagens**

- adequado para streaming ETL contínuo;
- utiliza Apache Spark Structured Streaming;
- bom para grandes volumes e transformações complexas;
- integra-se bem com Data Lakes em S3;
- adequado para processamento distribuído.

**Desvantagens**

- maior complexidade;
- custo superior para fluxo simples;
- mais adequado para streams contínuos de alto volume;
- desnecessário para eventos individuais de triagem;
- aumenta a complexidade operacional do MVP.

---

## Consequências

### Positivas

- menor esforço operacional;
- arquitetura serverless;
- integração direta com SQS;
- escalabilidade automática;
- menor custo para MVP;
- processamento próximo ao tempo real;
- facilidade de manutenção;
- separação clara entre processamento near real-time e processamento batch.

### Negativas

- necessidade de garantir idempotência;
- cuidado com timeout da função;
- necessidade de tratar mensagens duplicadas;
- maior atenção à configuração de batch size e visibility timeout;
- possível necessidade de evolução para containers ou streaming Spark caso o processamento se torne mais complexo.

---

## Riscos

- processamento duplicado de eventos;
- falha temporária do Identity Service;
- mensagens inválidas causando falha recorrente;
- timeout da função;
- exposição acidental de PII em logs;
- aumento inesperado de concorrência;
- escrita inconsistente entre Silver e Realtime Indicator Store.

---

## Mitigações

- uso de `event_id` para idempotência;
- logs estruturados sem CPF, nome ou documento;
- validação de schema antes do processamento;
- uso de DLQ para mensagens inválidas;
- configuração adequada de timeout;
- configuração de batch size compatível com o tempo de processamento;
- controle de concorrência quando necessário;
- métricas e alarmes no CloudWatch;
- uso de retries controlados;
- persistência apenas de dados anonimizados ou pseudonimizados.

---

## Estratégia de Idempotência

Como o SQS pode entregar mensagens mais de uma vez, a Lambda deverá processar eventos de forma idempotente.

Cada evento deverá possuir um identificador único:

```text
event_id
```

Antes de atualizar indicadores ou persistir dados tratados, a função deverá verificar se o evento já foi processado.

Caso o `event_id` já exista, o evento será ignorado ou tratado como duplicado.

---

## Estratégia de Tratamento de Falhas

Mensagens que falharem por erro temporário poderão ser reprocessadas automaticamente.

Mensagens inválidas, com schema incorreto ou conteúdo inconsistente, serão enviadas para uma Dead Letter Queue (DLQ), permitindo análise posterior sem bloquear o fluxo principal.

---

## Decisão Final

Para o BAIP, **AWS Lambda** é a melhor escolha para processamento near real-time por ser simples, serverless, integrada ao SQS e suficiente para o processamento de eventos de triagem hospitalar.

ECS/Fargate e Glue Streaming permanecem como alternativas futuras caso o processamento passe a exigir containers long-running, dependências complexas, alto volume contínuo ou transformações distribuídas em streaming.
