# ADR-011: Estratégia de Qualidade de Dados

- **Status:** Aceito
- **Data:** 2026-07-05
- **Decisores:** Leonardo Lucas Pereira

---

## Contexto

O BAIP integra dados de múltiplas fontes públicas e simuladas, incluindo dados epidemiológicos, climáticos, hospitalares e eventos near real-time.

Essas fontes podem apresentar problemas como:

- campos nulos;
- tipos incorretos;
- duplicidade;
- datas inválidas;
- códigos de município inconsistentes;
- schemas alterados;
- registros incompletos;
- valores fora do domínio esperado.

A plataforma precisa garantir que dados inválidos não sejam propagados para camadas analíticas sem controle.

Foram consideradas as seguintes alternativas:

- validações customizadas em PySpark;
- AWS Glue Data Quality;
- Great Expectations;
- Amazon Deequ.

---

## Decisão

Será adotada uma estratégia híbrida baseada em:

```text
Validações críticas em PySpark
+
AWS Glue Data Quality para regras de qualidade em tabelas catalogadas
+
Camada de quarentena para registros inválidos
```

As validações críticas serão executadas nos jobs de transformação, enquanto regras tabulares e monitoramento de qualidade serão aplicados sobre tabelas Silver e Gold.

---

## Arquitetura Proposta

```text
Bronze
  │
  ▼
Silver Transformation Job
  │
  ├── Validações de schema
  ├── Validações de domínio
  ├── Deduplicação
  ├── Quarentena de registros inválidos
  ▼
Silver
  │
  ▼
Glue Data Quality
  │
  ▼
Gold
```

---

## Tipos de Validação

### Validações de Schema

- presença de colunas obrigatórias;
- tipos de dados esperados;
- nomes de colunas padronizados.

### Validações de Domínio

- UF válida;
- código IBGE válido;
- doença dentro da lista esperada;
- datas dentro de intervalo aceitável.

### Validações de Consistência

- data de notificação maior ou igual à data de sintomas;
- município compatível com UF;
- valores numéricos não negativos.

### Validações de Duplicidade

- remoção de registros duplicados por chave natural;
- controle de `event_id` para eventos near real-time.

### Validações de PII

- CPF, nome, e-mail e telefone não podem existir na Silver, Gold ou DW;
- campos sensíveis devem ser removidos ou tokenizados antes do consumo analítico.

---

## Camada de Quarentena

Registros inválidos serão gravados em uma área específica:

```text
s3://baip-data-lake/quarantine/
```

A quarentena deverá conter:

- registro original;
- nome da regra violada;
- timestamp do processamento;
- nome do job;
- fonte de origem.

---

## Justificativa

A abordagem híbrida foi escolhida porque oferece equilíbrio entre controle técnico e governança.

Validações em PySpark permitem bloquear erros críticos durante o pipeline, enquanto AWS Glue Data Quality permite monitorar regras tabulares nas camadas catalogadas.

A camada de quarentena permite rastrear e analisar registros inválidos sem interromper toda a plataforma.

---

## Alternativas Consideradas

### Validações Customizadas em PySpark

**Resultado:** Selecionadas parcialmente.

**Vantagens**

- flexibilidade;
- controle total da lógica;
- fácil integração com jobs existentes;
- adequado para regras críticas.

**Desvantagens**

- exige manutenção manual;
- pode gerar duplicação de código;
- não oferece governança visual nativa.

---

### AWS Glue Data Quality

**Resultado:** Selecionado para tabelas catalogadas.

**Vantagens**

- integração com Glue;
- adequado para tabelas no Data Catalog;
- reduz necessidade de ferramenta externa;
- bom para regras padronizadas.

**Desvantagens**

- menos flexível que código customizado;
- exige configuração das regras;
- pode não cobrir todas as validações de negócio.

---

### Great Expectations

**Resultado:** Não selecionado no MVP.

**Vantagens**

- ferramenta madura;
- boa documentação de expectativas;
- relatórios ricos;
- independente de cloud.

**Desvantagens**

- adiciona dependência externa;
- exige configuração adicional;
- aumenta complexidade operacional.

---

### Amazon Deequ

**Resultado:** Não selecionado no MVP.

**Vantagens**

- forte para qualidade em Spark;
- bom para grandes volumes;
- adequado para profiling.

**Desvantagens**

- maior complexidade;
- exige implementação adicional;
- menos simples para o escopo atual.

---

## Consequências

### Positivas

- maior confiabilidade dos dados;
- menor risco de KPIs incorretos;
- controle sobre registros inválidos;
- melhoria na governança;
- documentação das regras de qualidade.

### Negativas

- aumento do tempo de processamento;
- necessidade de manutenção das regras;
- maior complexidade nos jobs;
- possibilidade de falsos positivos em regras mal definidas.

---

## Riscos

- regras incompletas;
- registros válidos enviados para quarentena;
- falhas silenciosas de qualidade;
- alterações de schema nas fontes;
- propagação acidental de PII.

---

## Mitigações

- testes automatizados das regras;
- monitoramento de volume de registros inválidos;
- alertas para falhas de qualidade;
- revisão periódica das regras;
- validação obrigatória de ausência de PII;
- documentação das regras no repositório.

---

## Decisão Final

O BAIP adotará uma estratégia híbrida de qualidade de dados, combinando validações críticas em PySpark, AWS Glue Data Quality para tabelas catalogadas e uma camada de quarentena para registros inválidos.

Essa abordagem oferece equilíbrio entre segurança, governança, simplicidade e flexibilidade.
