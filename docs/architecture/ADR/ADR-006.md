# ADR-006: Escolha da Mensageria para Processamento Near Real-Time

- **Status:** Aceito
- **Data:** 2026-07-05
- **Decisores:** Leonardo Lucas Pereira

---

## Contexto

O BAIP (Brazil Arbovirus Intelligence Platform) contempla um fluxo simulado de integração com Sistemas de Informação Hospitalares, onde novos atendimentos de pacientes com suspeita de arboviroses são publicados como eventos durante a triagem.

Esses eventos precisam ser recebidos pela plataforma de forma assíncrona, desacoplada e confiável, permitindo que a camada de processamento near real-time consuma as mensagens sem criar dependência direta entre o sistema hospitalar e os serviços internos do BAIP.

A solução de mensageria deve atender aos seguintes requisitos:

- desacoplar o sistema produtor dos eventos do processamento interno;
- absorver variações no volume de mensagens;
- permitir retentativas em caso de falha;
- suportar tratamento de mensagens inválidas;
- permitir integração simples com a camada de processamento;
- manter baixo custo operacional;
- exigir baixa complexidade para o escopo do projeto;
- suportar um SLA de atualização near real-time, com indicadores atualizados em até 1 minuto após a chegada do evento.

Foram consideradas as seguintes alternativas:

- Amazon SQS;
- Amazon Kinesis Data Streams;
- Amazon MSK / Apache Kafka.

---

## Decisão

Será utilizado **Amazon SQS** como solução de mensageria para o fluxo near real-time do BAIP.

A fila SQS será responsável por receber eventos de triagem publicados pelos Sistemas de Informação Hospitalares e disponibilizá-los para processamento assíncrono pela camada de processamento near real-time.

Para o escopo inicial do projeto, será utilizada uma **fila SQS Standard**, combinada com mecanismos de idempotência baseados em `event_id`.

---

## Arquitetura Proposta

```text
Hospital Information System
            │
            ▼
      Amazon SQS Queue
            │
            ▼
Realtime Processing Function
```

A fila SQS atuará como buffer entre o sistema hospitalar e o processador de eventos.

---

## Papel da Mensageria na Arquitetura

A mensageria tem como objetivo:

- desacoplar o produtor dos eventos;
- evitar perda de eventos em caso de falha temporária no processamento;
- permitir reprocessamento de mensagens;
- controlar picos de carga;
- reduzir dependência direta entre sistemas;
- permitir tratamento de mensagens inválidas por meio de Dead Letter Queue (DLQ).

---

## Justificativa

O Amazon SQS foi escolhido por ser uma solução simples, gerenciada e suficiente para os requisitos do BAIP.

O fluxo de eventos do projeto é composto por mensagens independentes de triagem hospitalar, onde cada evento representa uma ocorrência que pode ser processada individualmente.

O BAIP não exige, neste momento:

- múltiplos consumidores independentes lendo o mesmo stream;
- retenção prolongada para replay histórico;
- processamento contínuo de alto volume;
- ecossistema completo de event streaming;
- ordenação global estrita dos eventos.

Dessa forma, o SQS oferece o melhor equilíbrio entre simplicidade, custo, confiabilidade e integração com os demais serviços da arquitetura serverless.

---

## Alternativas Consideradas

### Amazon SQS

**Resultado:** Selecionado.

**Vantagens**

- serviço totalmente gerenciado;
- baixo custo operacional;
- integração nativa com AWS Lambda;
- suporte a retentativas;
- suporte a Dead Letter Queue (DLQ);
- adequado para workloads assíncronos;
- simples de implementar;
- reduz o acoplamento entre produtor e consumidor;
- suficiente para o volume e o SLA do BAIP.

**Desvantagens**

- não é uma plataforma completa de streaming;
- menor flexibilidade para múltiplos consumidores independentes;
- menor capacidade de replay histórico quando comparado a Kinesis ou Kafka;
- ordenação global não é garantida em filas Standard;
- pode gerar mensagens duplicadas, exigindo idempotência.

---

### Amazon Kinesis Data Streams

**Resultado:** Não selecionado para o escopo atual.

**Vantagens**

- adequado para alto volume contínuo de eventos;
- permite múltiplos consumidores;
- permite replay dentro da janela de retenção;
- bom para streaming analytics;
- adequado para cenários com eventos contínuos e particionamento por chave.

**Desvantagens**

- maior complexidade de implementação;
- exige maior cuidado com shards e throughput;
- custo e operação superiores ao necessário para o MVP;
- mais adequado para fluxos contínuos de alto volume;
- desnecessário para o fluxo simples de triagem hospitalar do BAIP.

---

### Amazon MSK / Apache Kafka

**Resultado:** Não selecionado para o escopo atual.

**Vantagens**

- ecossistema maduro de streaming;
- forte adoção em arquiteturas corporativas;
- suporte a múltiplos tópicos e consumidores;
- alta flexibilidade para arquiteturas orientadas a eventos;
- boa opção para plataformas de eventos corporativas.

**Desvantagens**

- maior complexidade operacional;
- maior custo;
- exige maior conhecimento técnico em Kafka;
- exige decisões adicionais sobre tópicos, partições, retenção e consumidores;
- excesso de capacidade para o volume e escopo inicial do BAIP.

---

## Consequências

### Positivas

- arquitetura simples e desacoplada;
- baixo custo inicial;
- integração direta com Lambda;
- menor esforço operacional;
- suporte a falhas por meio de retry e DLQ;
- solução adequada para o requisito near real-time do projeto;
- facilidade de evolução para soluções mais robustas no futuro.

### Negativas

- menor flexibilidade para múltiplos consumidores;
- menor capacidade de replay histórico;
- menos adequado para streaming analytics avançado;
- necessidade de tratar mensagens duplicadas;
- possível necessidade de evolução futura para Kinesis ou Kafka.

---

## Riscos

- processamento duplicado de mensagens;
- mensagens inválidas bloqueando o processamento;
- crescimento inesperado da fila;
- configuração inadequada de visibility timeout;
- perda de rastreabilidade caso o evento não possua identificador único;
- acúmulo de mensagens na DLQ sem tratamento.

---

## Mitigações

- utilização de `event_id` para garantir idempotência;
- configuração de Dead Letter Queue (DLQ);
- configuração adequada de visibility timeout;
- monitoramento do backlog da fila;
- alarmes para mensagens não processadas;
- logs estruturados sem exposição de PII;
- validação de schema antes do processamento;
- política de retenção adequada para as mensagens.

---

## Decisão Final

Para o escopo atual do BAIP, o **Amazon SQS** é a melhor opção por equilibrar simplicidade, baixo custo, confiabilidade e integração nativa com a arquitetura serverless proposta.

A evolução para **Amazon Kinesis Data Streams** ou **Amazon MSK / Apache Kafka** poderá ser considerada no futuro caso o projeto passe a exigir alto volume contínuo de eventos, múltiplos consumidores independentes, replay histórico avançado ou processamento de streaming analítico em larga escala.
