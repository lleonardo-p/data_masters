# ADR-005: Estratégia de Tokenização e Proteção de Dados PII

- **Status:** Aceito
- **Data:** 2026-07-05
- **Decisores:** Leonardo Lucas Pereira

---

## Contexto

O BAIP processa dados relacionados ao monitoramento de arboviroses no Brasil e contempla um fluxo simulado de integração com Sistemas de Informação Hospitalares (SI).

Nesse fluxo, são processados dados pessoais identificáveis (PII), como CPF, associados aos atendimentos realizados durante a triagem hospitalar.

Como o projeto envolve dados de saúde, é necessário garantir que informações pessoais não sejam propagadas para as camadas analíticas (Silver, Gold e Data Warehouse), atendendo aos princípios da LGPD e reduzindo o risco de exposição de dados sensíveis.

---

## Decisão

Será adotada uma estratégia de **tokenização de dados PII**.

Os dados pessoais identificáveis serão processados por um **Identity Service**, responsável por gerar um identificador técnico (`patient_id`) que substituirá o CPF em todo o pipeline analítico.

O `patient_id` será utilizado nas camadas Silver, Gold, Data Warehouse, APIs analíticas e dashboards.

O documento original permanecerá isolado em uma base segura de mapeamento, acessível apenas pelos serviços autorizados.

---

## Solução Proposta

O fluxo de anonimização será realizado conforme a arquitetura abaixo:

```text
Hospital Information System
            │
            ▼
      Identity Service
            │
            ▼
     PII Mapping Store
            │
            ▼
        patient_id
            │
            ▼
Pipeline Analítico (sem PII)
            │
            ▼
 Bronze → Silver → Gold → Data Warehouse
```

Fluxo de processamento:

1. O Sistema de Informação Hospitalar envia os dados da triagem.
2. O Identity Service recebe o CPF.
3. O serviço calcula um hash do documento utilizando SHA-256 + Salt.
4. O hash é utilizado para localizar um paciente já cadastrado.
5. Caso exista, o `patient_id` é reutilizado.
6. Caso não exista, um novo `patient_id` (UUID) é gerado.
7. O relacionamento entre documento e `patient_id` é armazenado no PII Mapping Store.
8. Apenas o `patient_id` segue para o pipeline de dados.

---

## PII Mapping Store

Será mantida uma base de dados exclusiva para gerenciamento da identidade dos pacientes.

Estrutura simplificada:

| Campo | Descrição |
|--------|-----------|
| document_hash | Hash SHA-256 + Salt do CPF |
| patient_id | Identificador técnico (UUID) |
| created_at | Data de criação |
| updated_at | Última atualização |
| status | Status do registro |

O CPF não será utilizado como chave de busca e não será propagado para as camadas analíticas.

---

## Justificativa

A tokenização foi escolhida por oferecer maior flexibilidade e segurança em comparação ao uso direto de hash como identificador analítico.

Essa abordagem permite:

- impedir a propagação de CPF pelo pipeline;
- manter um identificador estável para relacionamento entre eventos;
- permitir devolutiva individual ao paciente quando necessário;
- isolar dados sensíveis da camada analítica;
- reduzir o risco de exposição em dashboards e APIs;
- facilitar futuras evoluções relacionadas à governança de dados.

---

## Consequências

### Positivas

- isolamento completo dos dados PII;
- Data Lake e Data Warehouse livres de informações pessoais;
- menor risco de vazamento de dados sensíveis;
- aderência às boas práticas da LGPD;
- separação entre identidade e dados analíticos;
- suporte à rastreabilidade sem exposição do documento.

### Negativas

- aumento da complexidade da arquitetura;
- necessidade de manter um serviço dedicado para identidade;
- necessidade de proteger a base de mapeamento;
- dependência do Identity Service durante a ingestão.

---

## Alternativas Consideradas

### Hash direto do CPF

**Resultado:** Rejeitado

**Vantagens**

- implementação simples;
- identificador determinístico.

**Desvantagens**

- menor flexibilidade;
- dificulta futuras mudanças de identidade;
- dependência do algoritmo de hash como chave de negócio.

---

### Armazenar CPF nas camadas analíticas

**Resultado:** Rejeitado

**Vantagens**

- simplifica consultas individuais.

**Desvantagens**

- elevado risco de exposição de dados;
- não atende às boas práticas de proteção de PII;
- amplia a superfície de ataque.

---

### Criptografia reversível (AES)

**Resultado:** Rejeitado para o pipeline analítico.

**Vantagens**

- permite recuperar o documento original.

**Desvantagens**

- aumenta a complexidade de gerenciamento de chaves;
- amplia o risco em caso de comprometimento da chave de criptografia.

---

### Tokenização

**Resultado:** ✅ Selecionada

**Vantagens**

- separa identidade do pipeline analítico;
- permite reutilização do identificador técnico;
- facilita governança e auditoria;
- reduz exposição de dados pessoais;
- arquitetura amplamente utilizada em ambientes corporativos.

---

## Riscos

- acesso indevido ao PII Mapping Store;
- comprometimento do Salt utilizado para geração do hash;
- falhas no Identity Service;
- exposição de PII em logs;
- utilização incorreta do CPF fora da camada de identidade.

---

## Mitigações

- autenticação e autorização via AWS IAM;
- armazenamento do Salt no AWS Secrets Manager;
- criptografia em repouso utilizando AWS KMS;
- princípio do menor privilégio (Least Privilege);
- auditoria de acessos via AWS CloudTrail;
- validações automáticas para impedir propagação de PII para Silver, Gold e Data Warehouse.
