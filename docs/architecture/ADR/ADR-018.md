# ADR-018: Estratégia de Reconciliação entre Batch e Near Real-Time

- **Status:** Aceito
- **Data:** 2026-07-05
- **Decisores:** Leonardo Lucas Pereira

---

## Contexto

O BAIP possui dois fluxos principais de entrada de dados:

1. **Fluxo Batch**, responsável por ingerir dados públicos e oficiais, como OpenDataSUS, Open-Meteo, NASA EONET e bases de infraestrutura de saúde;
2. **Fluxo Near Real-Time**, responsável por processar eventos simulados de triagem hospitalar publicados por Sistemas de Informação Hospitalares.

Esses fluxos possuem naturezas diferentes.

O fluxo batch representa dados históricos, consolidados e mais próximos das fontes oficiais. Já o fluxo near real-time representa eventos operacionais recentes, ainda não necessariamente consolidados nas bases oficiais.

A existência desses dois fluxos gera um desafio arquitetural importante: evitar duplicidade e inconsistência entre indicadores batch e indicadores near real-time.

Exemplo do problema:

```text
10:30 → Hospital SI publica evento de suspeita de dengue
10:31 → Lambda processa evento e atualiza indicador near real-time

00:00 → Batch oficial carrega dados do OpenDataSUS
```

Caso o evento hospitalar também esteja presente posteriormente no batch oficial, existe risco de dupla contagem se os dois fluxos forem simplesmente somados.

---

## Decisão

Será adotada uma estratégia de **reconciliação entre batch e near real-time baseada em watermark, idempotência e janela de consolidação**.

O fluxo batch será considerado a fonte oficial para períodos já consolidados.

O fluxo near real-time será utilizado para complementar os indicadores apenas para eventos posteriores ao último período oficialmente consolidado pelo batch.

A regra principal será:

```text
Indicador consolidado =
dados batch até o watermark
+
eventos near real-time após o watermark
```

---

## Objetivo da Estratégia

A estratégia tem como objetivo:

- evitar dupla contagem de casos;
- separar dados oficiais de dados operacionais;
- permitir atualização near real-time dos indicadores;
- manter o Data Warehouse como camada analítica confiável;
- permitir reconciliação periódica entre fluxos;
- garantir rastreabilidade entre batch, streaming e Gold;
- impedir que o DynamoDB seja usado como fonte analítica final.

## Fluxo Batch

O fluxo batch será responsável por processar dados públicos e oficiais.

```text
OpenDataSUS / Open-Meteo / NASA / Infraestrutura
        │
        ▼
Bronze Ingestion Job
        │
        ▼
Bronze Data Lake
        │
        ▼
Silver Transformation Job
        │
        ▼
Silver Data Lake
        │
        ▼
Gold Analytics Job
        │
        ▼
Gold Batch Indicators
        │
        ▼
Update Batch Watermark
        │
        ▼
Data Warehouse
```

---

## Responsabilidades do Fluxo Batch

O fluxo batch será responsável por:

1. Extrair dados das fontes públicas;
2. Persistir dados brutos na camada Bronze;
3. Padronizar, limpar e enriquecer dados na camada Silver;
4. Gerar indicadores oficiais na camada Gold;
5. Construir ou atualizar fatos e dimensões do Data Warehouse;
6. Atualizar a tabela de controle `control_batch_watermark`;
7. Marcar até qual período os dados oficiais estão consolidados.

---

## Fluxo Near Real-Time

O fluxo near real-time será responsável por processar eventos simulados de triagem hospitalar.

```text
Hospital Information System
        │
        ▼
Amazon SQS
        │
        ▼
AWS Lambda
        │
        ├── Identity Service
        │
        ├── Silver Streaming Events
        │
        └── DynamoDB Realtime Indicators
```

---

## Responsabilidades do Fluxo Near Real-Time

O fluxo near real-time será responsável por:

1. Receber eventos de triagem hospitalar;
2. Validar o schema do evento;
3. Garantir idempotência por meio do `event_id`;
4. Resolver identidade via Identity Service;
5. Remover ou tokenizar dados PII;
6. Persistir o evento tratado na camada Silver;
7. Atualizar indicadores agregados no DynamoDB;
8. Disponibilizar indicadores operacionais em baixa latência.

---

## Papel do DynamoDB

O DynamoDB será utilizado como **store operacional near real-time**.

Ele não será considerado a fonte oficial de dados analíticos.

Seu papel será:

- armazenar contadores agregados atualizados rapidamente;
- permitir atualização atômica de indicadores;
- servir como camada temporária de baixa latência;
- alimentar a camada Gold por meio do Realtime Gold Sync Job.

Exemplo de item no DynamoDB:

```text
PK = SP#2026-07-03#DENGUE
total_cases = 501
last_update = 2026-07-03T10:30:00
source = hospital_si
```

---

## Realtime Gold Sync Job

O **Realtime Gold Sync Job** será responsável por sincronizar os indicadores near real-time armazenados no DynamoDB com a camada Gold.

```text
DynamoDB Realtime Indicators
        │
        ▼
Realtime Gold Sync Job
        │
        ▼
Gold Realtime Indicators
        │
        ▼
Data Warehouse / Consolidated View
```

---

## Responsabilidades do Realtime Gold Sync Job

O job de sincronização será responsável por:

1. Ler indicadores agregados do DynamoDB;
2. Identificar registros atualizados desde a última sincronização;
3. Aplicar regras de watermark;
4. Gravar os indicadores na camada Gold;
5. Evitar sobrescrita incorreta de dados oficiais batch;
6. Registrar métricas de execução;
7. Atualizar controle de última sincronização;
8. Disponibilizar os dados para o Data Warehouse e dashboards.

---

## Frequência de Sincronização

A sincronização poderá ocorrer em janelas curtas.

Exemplo:

```text
A cada 1 minuto
```

Essa frequência permite que dashboards apresentem indicadores próximos ao tempo real sem acoplar diretamente o consumo analítico ao DynamoDB.

---

## Watermark

Será criada uma tabela de controle chamada:

```text
control_batch_watermark
```

Essa tabela indicará até qual período o batch oficial já consolidou os dados.

Exemplo:

```text
source       = opendatasus
uf           = SP
disease      = DENGUE
cutoff_date  = 2026-07-03
cutoff_time  = 2026-07-03T23:59:59
batch_id     = batch-20260704-001
updated_at   = 2026-07-04T00:30:00
```

---

## Estrutura da Tabela de Watermark

```text
control_batch_watermark

source
uf
municipio
disease
last_batch_cutoff
last_batch_execution_id
updated_at
status
```

---

## Regra de Consolidação

A view ou tabela consolidada deverá aplicar a seguinte regra:

```text
Usar dados batch quando event_date <= last_batch_cutoff

Usar dados near real-time quando event_time > last_batch_cutoff
```

Representação lógica:

```sql
SELECT
    date,
    uf,
    municipio,
    disease,
    total_cases,
    'batch' AS data_origin
FROM fact_cases_batch
WHERE event_date <= last_batch_cutoff

UNION ALL

SELECT
    date,
    uf,
    municipio,
    disease,
    total_cases,
    'realtime' AS data_origin
FROM fact_cases_realtime
WHERE event_time > last_batch_cutoff;
```

## Exemplo Prático

### Situação

O batch oficial está consolidado até:

```text
2026-07-03 23:59:59
```

O DynamoDB contém eventos near real-time:

```text
2026-07-03 18:00:00 → SP → DENGUE → +1
2026-07-04 09:30:00 → SP → DENGUE → +1
```

### Regra

O evento de `2026-07-03 18:00:00` não entra mais no consolidado, pois já está coberto pelo batch.

O evento de `2026-07-04 09:30:00` entra no consolidado, pois ainda está fora da janela oficial do batch.

```text
Batch oficial até 2026-07-03 23:59:59
+
Realtime apenas após 2026-07-03 23:59:59
```

## Idempotência

Como eventos near real-time podem ser entregues mais de uma vez, cada evento deverá possuir um identificador único:

```text
event_id
```

A Lambda deverá garantir que um mesmo `event_id` não incremente os indicadores mais de uma vez.

Estratégias possíveis:

- tabela de controle de eventos processados;
- escrita condicional no DynamoDB;
- validação antes de incremento;
- controle por `source_system + source_event_id`.

---

## Eventos Atrasados

Eventos near real-time podem chegar atrasados.

Exemplo:

```text
event_time = 2026-07-03 18:00:00
ingestion_time = 2026-07-04 10:00:00
```

Nesse caso, a decisão será baseada no `event_time`, não no `ingestion_time`.

Se o `event_time` estiver dentro de um período já consolidado pelo batch, o evento não deverá impactar os indicadores consolidados sem reconciliação explícita.

Esses eventos poderão ser:

- armazenados para auditoria;
- enviados para quarentena;
- usados em processo futuro de reconciliação;
- ignorados no indicador consolidado caso já estejam cobertos pelo batch oficial.

---

## Fonte Oficial

O batch será considerado a fonte oficial para períodos fechados.

O near real-time será considerado uma visão operacional para períodos ainda não consolidados.

```text
Batch
→ fonte oficial histórica

Near Real-Time
→ visão operacional recente

Gold / Data Warehouse
→ visão analítica reconciliada
```

---

## Justificativa

A estratégia de watermark foi escolhida porque permite combinar dados batch e near real-time sem dupla contagem.

Essa abordagem oferece:

- separação clara entre dados oficiais e operacionais;
- consistência nos indicadores;
- rastreabilidade por origem;
- suporte a atualização near real-time;
- possibilidade de correção posterior pelo batch oficial;
- simplicidade de implementação;
- alinhamento com arquiteturas Lambda-like, onde batch e velocidade são conciliados na camada analítica.

---

## Alternativas Consideradas

### Somar Batch e Near Real-Time Diretamente

**Resultado:** Rejeitado.

**Vantagens**

- implementação simples;
- baixa complexidade inicial.

**Desvantagens**

- alto risco de dupla contagem;
- indicadores inconsistentes;
- difícil auditoria;
- baixa confiabilidade analítica.

---

### Usar Apenas Batch

**Resultado:** Rejeitado.

**Vantagens**

- maior simplicidade;
- maior consistência histórica;
- menor complexidade arquitetural.

**Desvantagens**

- não atende ao requisito near real-time;
- dashboards ficam dependentes da frequência do batch;
- menor capacidade de monitoramento operacional.

---

### Usar Apenas Near Real-Time

**Resultado:** Rejeitado.

**Vantagens**

- baixa latência;
- visão operacional rápida.

**Desvantagens**

- não substitui fontes oficiais;
- maior risco de inconsistência;
- menor confiabilidade histórica;
- pode ignorar correções e consolidações posteriores do batch.

---

### Usar DynamoDB como Fonte Final do Dashboard

**Resultado:** Rejeitado.

**Vantagens**

- baixa latência;
- acesso simples por chave.

**Desvantagens**

- não é adequado como Data Warehouse;
- dificulta consultas analíticas complexas;
- acopla dashboard a uma camada operacional;
- reduz governança;
- não resolve reconciliação histórica com batch.

---

### Watermark + Reconciliação

**Resultado:** Selecionado.

**Vantagens**

- evita dupla contagem;
- mantém batch como fonte oficial;
- permite visão near real-time;
- separa camadas operacionais e analíticas;
- permite rastreabilidade;
- facilita auditoria e reprocessamento.

**Desvantagens**

- aumenta complexidade da arquitetura;
- exige tabela de controle;
- exige regras claras de corte temporal;
- exige cuidado com eventos atrasados.

---

## Consequências

### Positivas

- indicadores mais consistentes;
- menor risco de dupla contagem;
- separação clara entre batch e streaming;
- uso correto do DynamoDB como store operacional;
- Gold e Data Warehouse permanecem como camadas analíticas governadas;
- dashboards consomem dados reconciliados.

### Negativas

- maior complexidade de implementação;
- necessidade de manter watermark;
- necessidade de validar eventos atrasados;
- necessidade de reconciliar divergências entre fontes.

---

## Riscos

- watermark incorreto;
- eventos atrasados sendo descartados indevidamente;
- duplicidade por ausência de idempotência;
- divergência entre DynamoDB e Gold;
- batch oficial com atraso;
- dashboard consumindo DynamoDB diretamente sem reconciliação.

---

## Mitigações

- atualização controlada do watermark ao final do batch;
- uso obrigatório de `event_id`;
- controle de eventos processados;
- validação de divergência entre batch e realtime;
- logs estruturados de sincronização;
- alarmes para falha do Realtime Gold Sync Job;
- documentação clara da regra de consolidação;
- exposição dos dashboards apenas sobre Gold/DW reconciliado.

---

## Estratégia de Consumo pelo Dashboard

O dashboard deverá consumir a camada analítica reconciliada.

Fluxo recomendado:

```text
Gold Batch Indicators
        │
        ▼
Consolidated Indicator View
        ▲
        │
Gold Realtime Indicators
        │
        ▲
Realtime Gold Sync Job
```

O dashboard não deverá consultar diretamente o DynamoDB como fonte principal.

O DynamoDB poderá ser utilizado apenas em cenários operacionais específicos, como APIs internas de monitoramento near real-time.

---

## Decisão Final

O BAIP adotará uma estratégia de reconciliação baseada em **watermark, idempotência e sincronização controlada entre DynamoDB e Gold**.

O fluxo batch será considerado fonte oficial para períodos consolidados, enquanto o fluxo near real-time será utilizado para complementar indicadores recentes ainda não cobertos pelo batch.

O DynamoDB será utilizado como store operacional de baixa latência, e o Realtime Gold Sync Job será responsável por sincronizar os indicadores near real-time com a camada Gold.

A camada Gold/Data Warehouse será a fonte analítica final para dashboards e APIs analíticas.
