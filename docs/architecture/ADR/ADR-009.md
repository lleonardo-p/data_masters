# ADR-009: Estratégia de Modelagem do Data Warehouse

- **Status:** Aceito
- **Data:** 2026-07-05
- **Decisores:** Leonardo Lucas Pereira

---

## Contexto

O BAIP precisa disponibilizar dados analíticos consolidados para acompanhamento de arboviroses no Brasil.

A plataforma integra dados epidemiológicos, climáticos, hospitalares e eventos near real-time, sendo necessário organizar essas informações em um modelo adequado para consumo por dashboards, APIs analíticas e consultas SQL.

A modelagem deve permitir:

- cálculo de indicadores epidemiológicos;
- análise por município, UF, região e período;
- análise por tipo de arbovirose;
- correlação entre casos, clima e infraestrutura de saúde;
- consumo eficiente por ferramentas de BI;
- separação entre dados operacionais e dados analíticos;
- ausência de dados pessoais identificáveis (PII).

Foram consideradas as seguintes alternativas:

- Star Schema;
- One Big Table (OBT);
- Data Vault.

---

## Decisão

Será adotada uma modelagem dimensional baseada em **Star Schema** para o Data Warehouse analítico do BAIP.

As tabelas fato e dimensão serão construídas a partir da camada Gold e disponibilizadas para consulta via camada analítica.

---

## Modelo Proposto

O Data Warehouse será composto por tabelas fato e dimensões.

### Tabelas fato

```text
fact_arbovirus_cases
fact_daily_case_indicators
fact_climate_daily
fact_health_capacity
fact_realtime_indicators
```

### Dimensões

```text
dim_date
dim_location
dim_disease
dim_health_unit
dim_hospital
dim_patient_profile
dim_source
```

---

## Grão das Tabelas

### fact_arbovirus_cases

```text
1 registro = 1 notificação de caso de arbovirose
```

### fact_daily_case_indicators

```text
1 registro = 1 agregado diário por município, doença e fonte
```

### fact_climate_daily

```text
1 registro = 1 medição climática diária por município
```

### fact_health_capacity

```text
1 registro = 1 consolidação de infraestrutura de saúde por município e período
```

### fact_realtime_indicators

```text
1 registro = 1 indicador near real-time por data, município, UF e doença
```

---

## Princípios de Modelagem

A modelagem seguirá os seguintes princípios:

- nenhuma tabela analítica deverá conter CPF, nome, telefone, e-mail ou outro dado PII;
- o `patient_id` pseudonimizado só poderá existir em tabelas restritas quando necessário;
- dashboards deverão consumir preferencialmente dados agregados;
- fatos devem representar eventos ou medidas;
- dimensões devem representar contexto analítico;
- chaves técnicas serão utilizadas para relacionamento entre fatos e dimensões;
- o Data Warehouse será otimizado para leitura e análise, não para operação transacional.

---

## Justificativa

O Star Schema foi escolhido por ser simples, amplamente utilizado em ambientes analíticos e adequado para consumo por ferramentas de BI.

Essa abordagem permite:

- consultas SQL mais simples;
- boa performance para dashboards;
- separação clara entre fatos e dimensões;
- facilidade de entendimento por usuários de negócio;
- organização dos KPIs epidemiológicos;
- evolução gradual do modelo analítico.

O Data Vault foi considerado excessivo para o escopo atual, enquanto a One Big Table reduziria a governança e aumentaria duplicidade de dados.

---

## Alternativas Consideradas

### Star Schema

**Resultado:** Selecionado.

**Vantagens**

- simples de entender;
- adequado para BI;
- boa performance analítica;
- separação clara entre fatos e dimensões;
- facilita construção de KPIs;
- amplamente utilizado em Data Warehouses.

**Desvantagens**

- exige desenho cuidadoso das dimensões;
- pode demandar manutenção conforme novas fontes são adicionadas;
- pode gerar múltiplas tabelas para governar.

---

### One Big Table (OBT)

**Resultado:** Não selecionada.

**Vantagens**

- simples para consumo inicial;
- reduz necessidade de joins;
- pode acelerar prototipação.

**Desvantagens**

- alta duplicidade de dados;
- menor governança;
- difícil manutenção;
- menor flexibilidade analítica;
- risco de acoplamento entre dashboard e estrutura física da tabela.

---

### Data Vault

**Resultado:** Não selecionado para o escopo atual.

**Vantagens**

- excelente para rastreabilidade;
- bom para múltiplas fontes;
- adequado para histórico e auditoria;
- escalável para ambientes corporativos complexos.

**Desvantagens**

- maior complexidade;
- maior curva de aprendizado;
- exige mais tabelas;
- excesso para o MVP do BAIP.

---

## Consequências

### Positivas

- modelo analítico simples e escalável;
- facilidade de consumo por dashboards;
- separação clara entre eventos, medidas e dimensões;
- melhor organização dos KPIs;
- redução do acoplamento com as fontes originais.

### Negativas

- necessidade de manutenção das dimensões;
- necessidade de definição clara do grão das tabelas;
- risco de inconsistência caso fatos e dimensões não sejam bem governados.

---

## Riscos

- duplicidade de registros em fatos;
- grão mal definido;
- dimensões inconsistentes;
- propagação indevida de PII;
- divergência entre dados batch e near real-time.

---

## Mitigações

- definição explícita do grão de cada tabela fato;
- uso de chaves técnicas;
- validações de qualidade antes da Gold;
- ausência de PII no Data Warehouse;
- documentação das tabelas e colunas;
- reconciliação entre indicadores batch e near real-time.

---

## Decisão Final

O BAIP utilizará **Star Schema** como estratégia de modelagem do Data Warehouse, com tabelas fato e dimensão construídas a partir da camada Gold.

Essa abordagem oferece o melhor equilíbrio entre simplicidade, governança, performance analítica e facilidade de consumo por dashboards.
