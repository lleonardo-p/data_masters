# ADR-010: Estratégia de Catálogo de Dados e Metadados

- **Status:** Aceito
- **Data:** 2026-07-05
- **Decisores:** Leonardo Lucas Pereira

---

## Contexto

O BAIP armazena dados em múltiplas camadas do Data Lake, seguindo a arquitetura Medallion:

```text
Bronze → Silver → Gold → Data Warehouse
```

Essas camadas contêm arquivos e tabelas derivados de diferentes fontes, como OpenDataSUS, Open-Meteo, NASA EONET e Sistemas de Informação Hospitalares simulados.

Para permitir descoberta, consulta e governança dos dados, é necessário manter um catálogo centralizado de metadados.

O catálogo deve permitir:

- registro de databases e tabelas;
- documentação de schemas;
- controle de partições;
- integração com mecanismos de consulta;
- suporte a Glue Jobs;
- descoberta de dados por camada e domínio;
- organização dos datasets analíticos.

Foram consideradas as seguintes alternativas:

- AWS Glue Data Catalog;
- Hive Metastore;
- DataHub;
- Catálogo manual em documentação Markdown.

---

## Decisão

Será utilizado **AWS Glue Data Catalog** como catálogo central de metadados do BAIP.

O Glue Data Catalog será responsável por registrar as tabelas das camadas Silver, Gold e Data Warehouse, permitindo consulta via Athena e integração com Glue Jobs.

---

## Arquitetura Proposta

```text
Amazon S3
  ├── Bronze
  ├── Silver
  ├── Gold
  └── Data Warehouse
          │
          ▼
AWS Glue Data Catalog
          │
          ▼
Amazon Athena
          │
          ▼
Dashboard / APIs Analíticas
```

---

## Escopo do Catálogo

O catálogo deverá registrar:

- nome da base de dados;
- nome da tabela;
- descrição da tabela;
- descrição das colunas;
- tipos de dados;
- partições;
- localização física no S3;
- camada da arquitetura;
- fonte de origem;
- periodicidade de atualização;
- classificação de sensibilidade.

## Justificativa

O AWS Glue Data Catalog foi escolhido por ser nativo no ecossistema AWS e integrado aos serviços utilizados no BAIP.

Essa escolha permite:

- integração direta com AWS Glue;
- consulta das tabelas via Amazon Athena;
- centralização dos metadados;
- descoberta de datasets;
- organização das camadas do Data Lake;
- redução da complexidade operacional.

Ferramentas como DataHub são mais completas para governança corporativa, mas adicionam complexidade além do necessário para o escopo atual.

---

## Alternativas Consideradas

### AWS Glue Data Catalog

**Resultado:** Selecionado.

**Vantagens**

- integração nativa com Glue;
- integração com Athena;
- serviço gerenciado;
- adequado para Data Lakes em S3;
- reduz esforço operacional;
- suficiente para o escopo atual do BAIP.

**Desvantagens**

- recursos de linhagem são limitados;
- menor riqueza funcional quando comparado a catálogos corporativos;
- exige disciplina na documentação dos metadados.

---

### Hive Metastore

**Resultado:** Não selecionado.

**Vantagens**

- amplamente utilizado no ecossistema Hadoop/Spark;
- compatível com workloads tradicionais de Big Data.

**Desvantagens**

- exige operação e manutenção;
- menos integrado ao stack serverless AWS;
- adiciona complexidade desnecessária.

---

### DataHub

**Resultado:** Não selecionado para o MVP.

**Vantagens**

- excelente para governança;
- suporte a linhagem;
- interface rica para descoberta de dados;
- adequado para ambientes corporativos.

**Desvantagens**

- maior complexidade operacional;
- exige infraestrutura adicional;
- excesso para o escopo atual.

---

### Catálogo Manual em Markdown

**Resultado:** Rejeitado como solução principal.

**Vantagens**

- simples;
- fácil de versionar no Git.

**Desvantagens**

- não integra com Athena;
- não registra partições;
- não serve como catálogo técnico de execução;
- fica rapidamente desatualizado.

---

## Consequências

### Positivas

- metadados centralizados;
- integração com Glue e Athena;
- descoberta de dados facilitada;
- melhor governança técnica;
- padronização de tabelas e schemas.

### Negativas

- necessidade de manter metadados atualizados;
- possível inconsistência se jobs gravarem dados sem atualizar o catálogo;
- recursos limitados de linhagem avançada.

---

## Riscos

- tabelas sem documentação;
- schemas desatualizados;
- partições não registradas;
- falta de classificação de sensibilidade;
- nomes inconsistentes.

---

## Mitigações

- padronização de nomenclatura;
- atualização do catálogo durante os pipelines;
- documentação das tabelas críticas;
- validação de schemas;
- revisão periódica dos metadados;
- classificação das tabelas por camada e sensibilidade.

---

## Decisão Final

O BAIP utilizará **AWS Glue Data Catalog** como catálogo central de metadados.

Essa decisão mantém a arquitetura simples, integrada ao ecossistema AWS e adequada ao consumo analítico via Athena.
